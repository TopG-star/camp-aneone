# Oneon: Roadmap v1.2 reconciliation and technical and UX review

**Date:** 2026-10-07
**Reviewed:** Roadmap v1.2 against the Oneon code on `feat/ai-data-boundary` (535e132), ImpressoRx `main` (a3ce5a3), the AI Data Boundary spec and its 1a and 1b plans, and the Action Spec framework.
**Method:** code and document reading. The UX findings come from component code, not a running app.

Severity: **High** means it blocks or contradicts a decision. **Medium** means it should be fixed in the step named. **Low** is polish.

**Rulings (Gerry, 2026-10-07).** The roadmap's errata record each one ([roadmap v1.2](../roadmap/2026-10-07-oneon-roadmap-v1.2.md), E1–E4).
- **R2:** suppliers are D2 by default, D1 only as a deliberate, declared exception. ImpressoRx already matches, so no map change.
- **R4:** personal D2 needs a full provider review record (the checklist in E2). Until one exists, DeepSeek and Anthropic run at personal D1.
- **R6:** flatten `metadata`.
- **Sequencing:** v1.1 code waits for the 1a merge.

The other R-items are proposals awaiting a ruling (P1–P9).

## Part 2. Technical review (MECE by concern)

### T-A Disclosure control (the gateway)
- **Sound:** one gateway; the `ApprovedModelCall` type that only the gateway can create; architecture test; default-deny classes; scanner backstop; audit without content; the fail-closed behaviours your 2026-10-04 review checked.
- **Med:** four third-party D2 strings skip the scanner at D2 (R6).
- **Med:** a raw `fetch` to a model API isn't caught by any test (R14).
- **Low:** at D1, chat drops its own earlier replies without telling the person (see U-C3).

### T-B Providers, routing and configuration
- **High:** routing for tiers versus roles needs a fallback rule (R3).
- **High:** a personal D2 ceiling has no review requirement (R4).
- **Med:** provider clients have no reasoning-effort parameter, which T3 assumes. Add it as an optional field on `ApprovedModelCall` when §6.5 starts.
- **Med:** out-of-date model defaults (R12); no cost table (R9).

### T-C Action execution (Step A)
- **Sound:** 15-status machine with allowed transitions; at execution, preconditions, `resolve`, the changed-since-approval check and policy re-run (`advance.ts` 135–195); idempotency keys; per-instance event sequence.
- **Med:** nothing links an action to the model call that proposed it (v1.2 §5 adds `model_call_id`).
- **Med:** no dry-run function yet (v1.2 §6.4).
- **Info:** the six Gmail actions are registered with no executor (missing scopes). Tenant actors throw by design until Step B.

### T-D Identity, authorization and tenancy (Step B readiness)
- **High (for Step B):** `ActorContext` is rebuilt locally, with no ImpressoRx re-check. The Step B spec isn't written.
- **Ready:** `model_call_decisions` already carries `tenant_id`, `membership_id` and `channel`; `action_instances` carries `scope`, `tenant_id` and `location_ids_json`.

### T-E Audit, retention and privacy
- **High (before Step B):** `action_events.data_json`, `actor_json` and `action_instances.input_json` hold content and are append-only (migration 014).
- **High (before Step B):** `ai_data_choices` has a foreign key to `users(id)`.
- **High (before Step B):** erasure via HMAC key destruction conflicts with the "keep every key version" rule. Counsel decides (v1.2 §9.1).
- **Med:** only the retention class `NONE` is built.

### T-F ImpressoRx side
- **Done:** 1b map, checker and gate (46 models).
- **High:** GitHub accepted a direct push to `main`, so branch protection doesn't force changes through PRs. The gate blocks a PR merge only if branch protection requires it.
- **Med:** the supplier classes must change to v1.2's decision (R2).
- **Info:** there's no read API for Oneon yet (phase 2), and the vendor API stays off-limits.

### T-G Notifications and delivery
- **Med:** `notify` confirms only that Oneon stored the notification. Web push is best effort and unchecked. v1.2 keeps system sends outside the Action Spec, which is consistent.
- **Info:** there's no email or Teams send executor. Delivery status for those channels waits on them (v1.2 §9.7).

### T-H Quality engineering and operations
- **Sound:** Oneon has 1,622 tests with one known flake; ImpressoRx has 588; both CIs run on pull requests.
- **Med:** the flaky `actions.route.test.ts` needs its ticket.
- **Med:** there's no `gh` CLI here, so PRs and tickets are manual.
- **Med:** the staging smoke test is still pending.

## Part 3. UX review (MECE by journey; read from code, not seen running)

### U-A Consent and control (Settings → AI data)
1. **High:** choosing D2 from a provider's dropdown saves straight away. The pending banner asks the person to check the provider's terms first, but the dropdown grants the same D2 in one click with no prompt. Give the dropdown the same confirmation step.
2. **Med:** the "Unreviewed" badge has no explanation. Add a one-line tooltip: "Oneon hasn't completed a vendor review; limits stay low."
3. **Low:** the subtitle says "about you", but D2 also releases other people's emails. Suggested: "What Oneon may send to AI providers from your account."
4. **Med (v1.2):** confirming a provider set needs a new layout. It should show the set version, its providers, and which ones only take effect after review (R5).

### U-B Transparency (Recent calls)
1. **Med:** deny reasons appear as raw codes ("Not sent: required_part_withheld"). Map each to plain words.
2. **Low:** shows the provider id, not its label.
3. **Low:** "N held back" can't be expanded. `withheld_json` already holds field names and reasons with no content, so a disclosure list is safe to show.

### U-C Degraded states
1. **Sound:** "Email sorting is paused" on Today links to Settings.
2. **Info:** the withheld-briefing note appears only in the chat tool. The briefing on Today has no AI summary at all (`today.route.ts`: "deferred").
3. **Med:** at D1, chat silently forgets its earlier answers, so "and the second one?" fails without explanation. Show a one-time hint the first time history replies are held back.

### U-D Consistency
1. **Low:** Today formats dates as en-US, AI data as en-GB. Use en-GB everywhere (Ghana uses day-month order).
2. **Low:** the routing warning says "the standard AI provider", which is internal role language. With tiers coming, use purpose words instead ("email sorting and tool choice").

### U-E Not reviewed here
The actions, inbox, finance and notifications screens weren't inspected for this review.

### U-F Design rules for what v1.2 adds
- **Takeover:** visible on the conversation. Hand-back is a deliberate button, never a timeout.
- **Delivery words:** sent, delivered, failed. Never "verified".
- **Dry-run:** the preview says "No records were created."
- **Pending providers:** a provider waiting for review shows "Applies after review", not a disabled control with no reason.
